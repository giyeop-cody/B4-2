# 이슈 #6: 자동 LocalStorage 대체가 원격 DB 실패를 가림

## 재현

환경변수를 모두 빼고 앱을 실행해도 `localDB`로 목록과 CRUD가 성공했다.
사용자는 배포의 Supabase 설정이 빠진 사실을 화면에서 알 수 없었다.

## 원인

`api.js`가 “Supabase가 설정됐는가?”만 확인하고 아니면 무조건 LocalStorage를 골랐다.
개발 편의를 위한 대체 기능과 과제 필수 기능을 구분하지 않았다.

## 선택지와 결정

| 선택 | 장점 | 단점 |
|---|---|---|
| LocalStorage 삭제 | 원격 조건이 가장 분명함 | 인터넷 없는 기초 연습 불가 |
| 자동 대체 유지 | 앱이 항상 열림 | 원격 실패를 숨겨 과제 조건 위반 가능 |
| 명시적 학습 모드 | 연습과 원격 검증을 모두 구분 | 환경변수 하나를 더 이해해야 함 |

`VITE_ALLOW_LOCAL_DB=true`일 때만 로컬 저장소를 쓰는 세 번째 방법을 선택했다.
Supabase URL과 키가 있으면 로컬 허용값보다 원격을 먼저 고른다.

## 구현

- `dataSource.js`: `supabase`, `local`, `missing` 중 하나를 결정
- `api.js`: `missing`이면 이해할 수 있는 설정 오류를 던짐
- `DataSourceBadge`: 현재 저장 위치를 헤더에 표시
- `.env.example`: 로컬 모드는 배포에서 켜지 말라고 설명
- `verify-remote-crud.mjs`: 원격 생성→조회→수정→삭제 자동 검사
- 상세 조회는 `.maybeSingle()`을 사용해 없는 행을 빈 상태로 처리
- 수정·삭제는 없는 행이면 오류를 표시

## 재검사

- 데이터 선택 단위 테스트 3개 통과
- 전체 단위 테스트 10개 통과
- 제품 빌드 통과
- 실제 Supabase: CREATE 201, READ 200, UPDATE 200, DELETE 200
- 검사 행은 마지막에 삭제됨

## 배운 점

Fallback은 실패를 감추는 용도로 쓰면 안 된다. 학습용 대체 기능이면 사용자가 직접 켰다는 표시와 범위가 필요하다.
