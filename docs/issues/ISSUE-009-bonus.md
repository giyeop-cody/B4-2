# 이슈 #9: 보너스 3개가 구현되지 않음

## 기준선

- 전역 상태: 없음
- 메모이제이션: 없음
- Supabase Auth 로그인/보호 라우트: 없음

사용자 요청에 따라 선택 보너스도 이번 완료 범위에 넣었다.

## 1. 전역 상태

`AuthContext`가 로그인 사용자, 세션 확인 중, 세션 오류를 앱 전체에 제공한다.
`Layout`, `ProtectedRoute`, `LoginPage`, `ProfilePage`가 같은 사용자 상태를 읽는다.

### 선택 이유

테마보다 로그인 사용자가 인증 보너스와 바로 연결되어 중복 학습을 줄인다.
Context는 작은 앱에 충분하고, Redux 같은 별도 도구보다 배울 개념이 적다.
앱이 커지면 Context 값 변경이 많은 자식을 다시 그릴 수 있다는 한계가 있다.

## 2. 성능 최적화

- `useMemo`: 카테고리별 개수와 필터 결과를 items/category가 바뀔 때만 계산
- `React.memo`: 같은 item과 onDelete를 받은 `ItemCard` 다시 그리기 생략
- `useCallback`: 카드에 주는 삭제창 열기 함수와 오류 초기화 함수의 참조 고정

`React.memo`만 쓰고 매번 새 함수를 props로 보내면 비교가 실패하므로 세 가지를 같이 연결했다.
작은 목록은 계산이 매우 싸서 실제 속도 이득보다 비교 비용이 클 수 있다. 이번 적용은 동작 원리 학습 목적이며,
실서비스에서는 Profiler로 측정한 다음 유지할지 결정해야 한다.

## 3. 인증과 보호 라우트

- `/login`: 이메일 로그인과 회원가입
- `/profile`: `ProtectedRoute`가 지키는 화면
- 로그인 전 `/profile` 접근: `/login?redirect=%2Fprofile`로 이동
- 로그인 후: 원래 요청한 주소로 이동
- 로그아웃: 전역 사용자 상태를 즉시 비움

필수 CRUD는 평가 시 계정 문제로 막히지 않도록 공개 라우트로 유지했다.
이 보호 라우트는 프론트엔드 화면 보호 학습이다. 실제 데이터 권한 보호에는 Supabase RLS 정책이 별도로 필요하다.

## 원격 Auth 설정 실증

2026-08-14에 배포 번들의 공개 설정으로 `/auth/v1/settings`를 조회했다.

- HTTP 200
- 이메일 제공자: 활성
- 회원가입 차단: false
- 이메일 자동 확인: false (가입 뒤 이메일 확인 필요)

실제 타인의 이메일 계정을 임의로 만들지 않았다. UI 테스트에서는 가입 후 세션이 없을 때 이메일 확인 안내가 나오는 흐름을 검사했다.

## 재검사

- 보호 라우트 3상태: 확인 중, 비로그인, 로그인 통과
- 로그인 폼: 잘못된 입력 차단, 이메일 확인 안내
- 카테고리 필터: 개수와 변경 이벤트
- 전체: 테스트 파일 7개, 테스트 20개 통과
- 제품 빌드 통과
