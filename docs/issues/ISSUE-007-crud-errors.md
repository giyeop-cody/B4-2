# 이슈 #7: CRUD 실패와 제출 상태가 일부 화면에서 사라짐

## 재현

- 등록 실패: `useItems`에는 오류가 생기지만 `ItemNewPage`가 오류를 꺼내지 않아 화면에 안 보였다.
- 수정 시작: `useItem.updateItem`이 조회용 `loading`을 true로 바꾸어 폼 전체가 스피너로 사라졌다.
- 상세 삭제: 삭제를 위해 `useItems()`를 새로 호출하여 필요 없는 목록 조회도 실행했다.
- 상세 조회 실패: 다시 시도 함수를 `StateView`에 주지 않아 재시도 버튼이 없었다.

## 원인

조회 상태와 등록·수정·삭제 상태를 같은 `loading/error`로 관리했다.
페이지는 훅이 만든 모든 오류를 UI에 연결하지 않았다.

## 선택지

| 선택 | 장점 | 단점 |
|---|---|---|
| 상태 하나 계속 사용 | 코드가 짧음 | 어떤 작업 중인지 구분이 안 됨 |
| 조회/변경 상태 분리 | 폼과 오류가 정확히 남음 | 상태 이름이 늘어남 |

사용자가 보는 흐름을 분명히 하기 위해 `error`와 `mutationError`를 나눴다.

## 해결

- 조회 중에만 `loading` 사용
- 폼 버튼은 페이지의 `submitting` 사용
- 변경 실패는 `mutationError`로 폼 또는 페이지에 표시
- 상세 삭제를 `useItem.deleteItem`으로 이동해 불필요한 목록 조회 제거
- 상세·수정 화면에 `refetch` 연결
- 등록 성공 시 생성된 항목의 상세 화면으로 이동

## 재검사

- ItemForm 테스트에 원격 실패 표시 검사를 추가하여 총 11개 테스트 통과
- 제품 빌드 통과
- 삭제 대화상자의 진행 상태와 내부 오류 표시는 접근성 이슈 #13에서 이어서 개선한다.

## 배운 점

`loading`이라는 말이 같아도 “처음 읽는 중”과 “저장하는 중”은 사용자가 보는 화면이 다르다. 상태 이름을 실제 행동에 맞게 나누어야 한다.
