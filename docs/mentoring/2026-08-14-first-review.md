# 2026-08-14 첫 멘토·학습 동료 검토 기록

> 아래의 민지와 준호는 학습을 돕기 위해 정한 **페르소나**다. 외부 사람에게 받은 실제 평가는 아니다.

## 참여 역할

- 나(학생): 문과 중졸 수준에서 모르는 말을 하나씩 확인하며 구현한다.
- 민지(학습 멘토 페르소나): 과제 문장과 구현이 맞는지 질문한다.
- 준호(학습 동료 페르소나): 사용자가 실제로 겪을 문제를 찾아본다.

## 대화 1: 자동 대체가 안전한가?

**나:** Supabase 설정이 없을 때 LocalStorage로 바꾸면 앱이 안 죽어서 더 안전하다고 생각했다.

**민지:** 개발 연습에는 편하지만, 과제는 “원격 데이터 기준”이라고 적혀 있다. 배포 설정이 빠져도 성공한 것처럼 보이면 평가자가 문제를 발견하기 더 어렵다.

**나:** 그러면 LocalStorage를 완전히 지워야 할까?

**민지:** 두 선택지가 있다.

| 선택 | 장점 | 단점 |
|---|---|---|
| LocalStorage 삭제 | 구조가 단순하고 원격 조건이 분명함 | 인터넷 없이 기초 연습하기 어려움 |
| 명시적 학습 모드로만 허용 | 연습 가능, 배포 실패도 숨기지 않음 | 설정 분기가 조금 남음 |

**결정:** 두 번째를 선택한다. `VITE_ALLOW_LOCAL_DB=true`를 직접 넣은 로컬 실행에서만 허용한다.

## 대화 2: 인증으로 CRUD를 모두 막을까?

**나:** 보호 라우트를 만들려면 등록과 수정을 전부 로그인 뒤로 보내야 할까?

**준호:** 그러면 평가자가 계정 확인 문제 때문에 필수 CRUD를 못 볼 수 있다. 필수 기능과 보너스 기능이 서로 방해할 수 있다.

| 선택 | 장점 | 단점 |
|---|---|---|
| CRUD 쓰기 화면 보호 | 실제 서비스에 가까움 | 평가와 시연 때 계정 준비가 꼭 필요함 |
| 프로필 페이지만 보호 | 필수 CRUD 시연이 쉬움 | CRUD 권한 보호까지는 하지 않음 |

**결정:** 이번 과제의 중심은 React CRUD이므로 `/profile`을 보호 라우트로 만든다. 로그인 사용자는 전역 Context로 관리한다. 데이터 권한 고급 설정은 필수가 아니므로 범위를 늘리지 않는다.

## 대화 3: 무엇을 먼저 테스트할까?

**준호:** 모든 화면을 한 번에 자동화하려 하지 말고 실수하기 쉬운 작은 규칙부터 확인하자.

**결정한 순서:**

1. `StateView`의 로딩/에러/빈/성공 네 갈래
2. `ItemForm` 필수값과 제출 중 버튼
3. 보호 라우트의 로그인 전 이동
4. 데이터 계층의 명시적 모드
5. 빌드와 실제 Supabase CRUD 확인

## 이번에 배운 점

- “앱이 어떻게든 동작함”과 “과제 조건대로 동작함”은 다르다.
- 필수 기능과 보너스 기능이 서로 막지 않도록 범위를 정해야 한다.
- 테스트는 큰 기능 하나보다 작은 규칙부터 만들면 이해하기 쉽다.
