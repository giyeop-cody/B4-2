# 공개 조회 + 로그인 쓰기 평가 설명 자료

- 평가 기준일: 2026-08-14
- 기능 브랜치: `feature/authenticated-item-writes`
- 관련 기록: `docs/issues/ISSUE-022-authenticated-item-writes.md`
- 주의: 이 문서는 평가 준비 자료이며 실제 외부 동료의 서명·평가를 대신하지 않는다.

## 1. 30초 설명

목록과 상세는 누구나 볼 수 있다. 등록·수정·삭제는 Supabase에 로그인한 사용자만 할 수 있다. 비로그인 사용자는 등록 CTA를 누르면 원래 목적지를 담은 로그인 화면으로 이동하며 수정·삭제 메뉴는 보이지 않는다. 등록·수정·프로필 주소는 보호 라우트다. 작성자 소유권은 이번 범위에서 제외했다.

## 2. 요구사항 평가표

| 평가 항목 | 기대 결과 | 코드/로컬 결과 | 외부 결과 |
|---|---|---|---|
| 익명 목록 조회 | 가능 | 구현·테스트 통과 | 배포 E2E·REST 200 통과 |
| 익명 상세 조회 | 가능 | 구현·테스트 통과 | 배포 E2E 통과 |
| 익명 등록 CTA | 로그인으로 이동 | 구현·E2E 작성 | 배포 E2E 통과 |
| 익명 수정·삭제 UI | 보이지 않음 | 컴포넌트 테스트 통과 | 배포 E2E 통과 |
| 등록 보호 라우트 | 로그인으로 이동 | 구현, LocalStorage 예외 E2E 통과 | 배포 E2E 통과 |
| 수정 보호 라우트 | 로그인으로 이동 | 구현, LocalStorage 예외 E2E 통과 | 배포 수동 확인 통과 |
| 프로필 보호 라우트 | 로그인으로 이동 | 기존 테스트 통과 | 실제 계정 수동 확인 통과 |
| 로그인 CRUD | 가능 | 코드 구현 | 실제 계정 등록·수정·삭제 통과 |
| API mutation 세션 검사 | 세션 없으면 거절 | 구현 | 익명 mutation HTTP 401 |
| 공개 SELECT RLS | `anon`, `authenticated` 허용 | SQL 작성 | Dashboard 적용·REST 200 |
| 쓰기 RLS | `authenticated`만 허용 | SQL 작성 | 정책 3개·익명 REST 401 |
| 작성자 소유권 | 이번 범위 아님 | `user_id` 추가 안 함 | 해당 없음 |

## 3. 자동 검사 증거

- `npm test`: 10개 파일, 28/28 통과
- `npm run test:e2e`: 로컬 2개 통과, 배포 전용 2개 skip
- `npm run build`: 통과
- `npm audit --omit=dev`: 취약점 0개
- `git diff --check`: 통과
- Vercel Production Deployment: `success`
- 배포 익명 E2E: 1/1 통과
- 익명 REST: SELECT 200, INSERT/UPDATE/DELETE 401
- 실제 계정 수동: 등록·수정·삭제·프로필·로그아웃 통과

배포 검사는 두 종류로 나눴다.

1. `npm run test:e2e:production`: 계정 없이 익명 조회와 쓰기 UI 차단 검사
2. `PLAYWRIGHT_AUTH_EMAIL=... PLAYWRIGHT_AUTH_PASSWORD=... npm run test:e2e:production:write`: 확인된 계정으로 로그인 UI CRUD 검사

자격 증명은 환경변수로만 전달하고 저장소에 기록하지 않는다.

## 4. 설계 질문과 답변

### Q1. 버튼만 숨기면 충분한가?

아니다. 주소를 직접 입력하거나 API를 직접 호출할 수 있다. 그래서 UI, 보호 라우트, API 세션 검사, 데이터베이스 RLS의 네 겹을 사용한다.

### Q2. 왜 목록과 상세는 공개인가?

사용자가 로그인 전에 내용을 볼 수 있어 접근성이 좋다. 데이터 훼손 위험이 있는 쓰기만 로그인으로 제한해 조회 편의와 안전성의 균형을 잡았다.

### Q3. 왜 작성자 본인만 수정하도록 하지 않았나?

그 기능에는 `items.user_id`, 기존 행 이관, 작성자 표시, 소유권 RLS가 필요하다. 사용자가 이번 범위에서는 복잡도를 늘리지 말라고 정했으므로 로그인 사용자 전체 쓰기로 제한했다.

### Q4. 왜 LocalStorage 학습 모드는 로그인 없이 쓸 수 있나?

LocalStorage는 원격 서비스가 아니라 자신의 브라우저 안 연습 데이터다. `VITE_ALLOW_LOCAL_DB=true`로 직접 켠 경우에만 예외를 허용해 Supabase 계정 없이 CRUD를 배울 수 있게 했다. 배포에서는 이 값을 `false`로 둔다.

### Q5. 왜 SQL 파일을 작성한 시점에는 미완료라고 했나?

Git 파일은 실행 계획일 뿐 실제 데이터베이스 설정이 아니기 때문이다. 이후 프로젝트 소유자가 Dashboard SQL Editor에서 실행해 정책 네 개를 확인했고, 익명 거절과 로그인 성공까지 확인한 뒤 완료로 바꿨다.

## 5. 평가자가 직접 확인할 순서

1. 로그아웃 상태로 `/#/items`를 열어 목록을 확인한다.
2. `로그인 후 등록`을 누르고 로그인 주소의 `redirect=/items/new`를 확인한다.
3. 다시 목록과 상세에서 수정·삭제 메뉴가 없는지 확인한다.
4. 주소창에 `/#/items/new`와 유효한 `/#/items/{id}/edit`를 입력해 로그인 이동을 확인한다.
5. 평가용 계정으로 로그인해 등록 → 상세 → 수정 → 삭제를 확인한다.
6. 프로필과 로그아웃을 확인한다.
7. Supabase 정책 목록과 익명 mutation 거절 결과를 확인한다.

## 6. 외부 동료평가 기록란

- 평가 날짜: 미작성
- 직접 확인한 환경: 미작성
- 발견한 문제: 미작성
- 개선 의견: 미작성
- 수정 후 재확인: 미작성

외부 동료가 참여하지 않은 상태에서 이름, 점수, 합격 결과를 임의로 만들지 않는다.
